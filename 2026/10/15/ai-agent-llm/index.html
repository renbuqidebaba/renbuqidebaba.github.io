这一篇是我面试准备过程中整理的 Agent 与大模型相关笔记。和算法那批不同，这里更偏工程实践——Agent 的组件拆解、工具设计、MCP / Skills 的运行机制、上下文工程，以及 Transformer 推理侧的几个高频问题。内容以我自己的理解为主，参考资料随文标注。

一、Agent 的骨架

Agent 的核心组件

我把 Agent 拆成五块，缺一块都会明显影响上限：

  • 规划模块（Planning）——理解用户意图，把任务拆成可执行的步骤
  • 工具调用（Tool Calling）——连接外部工具和 API，让模型能作用于真实世界
  • 记忆管理（Memory）——短期记忆（当前会话）与长期记忆（跨会话的经验与知识）
  • 反思与修正（Reflection）——根据执行结果回头看，修正下一轮策略
  • 模型——选择最合适的模型做推理，不一定是最大的那个

ReAct：推理与行动交替

ReAct（Reasoning + Acting）是一种 Agent 框架，核心是让推理和行动交替进行来完成任务，有点类似现在 plan + exec 的工作流。

但我觉得原版 ReAct 缺一环：应该再叠一个反思模块，把执行结果反过来指导下一轮，让下一轮执行得更好。这也是后来 Reflexion 这类工作补上的部分。

上下文工程 ≠ 提示词工程

这两个词经常被混用，我的理解是提示词工程是上下文工程的一个子集：

维度 提示词工程 上下文工程
关注点 如何设计问题 / 指令本身 如何构建背景信息供模型参考
操作对象 用户输入的查询语句 系统提供的参考材料（文档、数据、历史记录）
目标 让模型更好地理解意图 让模型基于准确、相关的信息作答
技术栈 角色设定、思维链、Few-shot RAG、文档切分、向量检索、重排序

二、RAG

是什么

RAG = Retrieval Augmented Generation，检索增强生成。拆开就是三步：

  1. 去知识库检索相关内容
  2. 把检索结果融合进 prompt，增强输入信息
  3. 大模型基于增强后的输入，生成更符合事实的回答

评价指标

评估 RAG 要从「找得准」和「答得对」两个维度入手，单纯看准确率是不够的。

检索阶段：

  • 召回率 Recall@K——最重要的指标。Top K 个结果中至少包含一个正确答案的概率，K 通常取 3 或 5。召回率低意味着知识库设计或检索策略失败
  • 精确率 Precision@K——Top K 结果中相关文档的比例
  • MRR（Mean Reciprocal Rank）——衡量第一个正确答案出现的位置，越靠前得分越高

生成阶段：

  • 忠实度 Faithfulness——答案是否严格基于检索到的上下文。这是 RAG 的底线，用于防幻觉；忠实度低说明模型在胡编
  • 答案相关性 Answer Relevance——生成的答案是否直接回答了问题，而非答非所问
  • 引用准确率 Citation Accuracy——答案中的引用是否真的支持该论断

RAG 和微调怎么选

最佳实践是 RAG 为主、微调为辅：用 RAG 解决 80% 的知识问题，用微调优化剩下 20% 的特定场景。

Rerank 模型：原理与作用

作用：对召回返回的多篇文档重新排序，把最相关的排到前面，提升 RAG 精度。

原理：输入是 <query, doc> 对，通过双塔或交叉注意力模型计算相关性分数，按分数重排。交叉编码器效果更强但速度慢，双塔速度快但效果略弱。

分块策略

  • 固定长度分块——按长度机械切分
  • 语义分块——按句子、段落的语义完整性拆分
  • 递归分块——先切成大段，再看大小决定是否继续切小
  • 基于文档结构分块——按 PDF / Word 的标题层级划分

三、工具设计的哲学

这部分是我觉得最容易被低估的地方。

Tool 的本质

Tool 不是简单的 API 包装，它的本质是封装了确定性的计算逻辑，把 LLM 不确定的推理能力与确定性的外部系统连接起来——是可被 LLM 理解、调用的标准化功能模块。

所以设计的时候视角要换：普通函数面向程序员，Tool 面向 LLM。

# ❌ 普通函数 - 面向程序员
def search_database(query: str, db_connection) -> List[Result]:
    """直接操作数据库，需要连接对象"""

# ✅ Tool 设计 - 面向 LLM
def search_products(keywords: str, category: str = None, max_results: int = 10) -> str:
    """
    根据关键词搜索产品信息
    Args:
        keywords: 搜索关键词，如"笔记本电脑"
        category: 可选的产品类别，如"电子产品"
        max_results: 最大返回数量，默认为10
    Returns:
        产品信息的格式化字符串
    """

什么时候该做成 Tool？需要外部数据源、需要精确数据、会改变状态——这三种情况。另外每个 Tool 只管理一个领域的事情，别做万能函数。

元数据要写全

为了让 Agent 能智能选工具，元数据得给足：

{
  "tool_name": "calculate_loan_repayment",
  "description": "计算贷款月供和总利息",
  "category": "finance",
  "input_schema": {
    "principal": {"type": "number", "description": "贷款本金"},
    "annual_rate": {"type": "number", "description": "年利率(%)"},
    "months": {"type": "integer", "description": "贷款月数"}
  },
  "output_schema": {
    "monthly_payment": {"type": "number"},
    "total_interest": {"type": "number"}
  },
  "estimated_cost": 0.001,   // 调用成本
  "execution_time": 0.1,     // 设计调用的超时时间
  "success_rate": 0.99,      // 历史成功率
  "version": "1.2",
  "last_updated": "2024-01-15"
}

estimated_cost、execution_time、success_rate 这几个字段很多人会漏，但它们才是让 Agent 能做「性价比取舍」的依据。

四、MCP、Skills、Function Call 的区别

先把三者的层级关系摆清楚：

  • Function Call——模型与客户端之间的单次函数调用格式，是最小单元
  • MCP 协议——AI 与外部服务之间的完整双向通信协议（连接 + 会话 + 工具 + 资源）
  • Skills 协议——技能包。每一种方式调用时都必须进行强 schema 约束

MCP 协议（2024 年 12 月）

MCP（Model Context Protocol）定义了应用程序和 AI 模型之间交换上下文信息的方式，让开发者能以一致的方式把各种数据源、工具和功能连接到 AI 模型。定位是一个中间协议层。

底层实现：

  • 基于 JSON-RPC 2.0
  • SSE 作为长连接下行通道（服务端 → 客户端推送）
  • HTTP POST 作为上行请求通道（客户端 → 服务端调用）
  • 对比 stdio：SSE 方式适合跨机器 / 远程分布式 Agent 调用，打通网络级别的 MCP Host ↔ Server

执行流程：

  1. 客户端（Claude Desktop / Cursor）把你的问题发送给 Claude
  2. Claude 分析可用工具，决定使用哪一个或多个
  3. 客户端通过 MCP Server 执行所选工具
  4. 工具执行结果送回给 Claude
  5. Claude 结合结果构造最终 prompt，生成自然语言回应
  6. 回应展示给用户

智能体是怎么选工具的？

答案很朴素：靠 prompt engineering。把所有工具的结构化描述和 few-shot 示例塞进 system prompt，让模型自己选。

async def start(self):
    # 初始化所有的 mcp server
    for server in self.servers:
        await server.initialize()

    # 获取所有的 tools
    all_tools = []
    for server in self.servers:
        tools = await server.list_tools()
        all_tools.extend(tools)

    # 将所有的 tools 的功能描述格式化成字符串供 LLM 使用
    tools_description = "\n".join(
        [tool.format_for_llm() for tool in all_tools]
    )

    system_message = (
        "You are a helpful assistant with access to these tools:\n\n"
        f"{tools_description}\n"
        "Choose the appropriate tool based on the user's question. "
        "If no tool is needed, reply directly.\n\n"
        "IMPORTANT: When you need to use a tool, you must ONLY respond with "
        "the exact JSON object format below, nothing else:\n"
        "{\n"
        '    "tool": "tool-name",\n'
        '    "arguments": {\n'
        '        "argument-name": "value"\n'
        "    }\n"
        "}\n\n"
        "After receiving a tool's response:\n"
        "1. Transform the raw data into a natural, conversational response\n"
        "2. Keep responses concise but informative\n"
        "3. Focus on the most relevant information\n"
        "4. Use appropriate context from the user's question\n"
        "5. Avoid simply repeating the raw data\n\n"
        "Please use only the tools that are explicitly defined above."
    )

模型分析用户请求后，会决定是否需要调用工具：

  • 无需工具——直接生成自然语言回复
  • 需要工具——输出结构化 JSON 格式的调用请求

如果回复里含工具调用请求，客户端就按这个 JSON 执行对应工具。执行结果再和 system prompt、用户消息一起发回给模型，请它生成最终回复。

那如果 tool call 的 JSON 有问题、或者模型产生幻觉呢？skip 掉无效的调用请求就行。

while True:
    messages.append({"role": "user", "content": user_input})
    llm_response = self.llm_client.get_response(messages)

    # 处理 LLM 的输出（如果有 tool call 则执行对应的工具）
    result = await self.process_llm_response(llm_response)

    # result 与 llm_response 不同，说明执行了 tool call
    if result != llm_response:
        messages.append({"role": "assistant", "content": llm_response})
        messages.append({"role": "system", "content": result})
        final_response = self.llm_client.get_response(messages)
        messages.append({"role": "assistant", "content": final_response})
    else:
        # 没有执行 tool call，直接返回
        messages.append({"role": "assistant", "content": llm_response})

两个结论：

  • 工具文档至关重要——模型通过工具描述文本来理解和选择工具，所以名称、docstring、参数说明都要精心写
  • 任何模型都能适配 MCP——因为选择是基于 prompt 的，只要你能提供对应的工具描述

Claude Skills（2025 年 10 月）

Skills 是 Claude 的可扩展机制。每个 Skill 本质上是一个文件夹，包含元数据、说明文档，以及可选的代码脚本和资源文件。

关键在于渐进式加载——不是一次性全塞进上下文：

在系统层面，Claude 为技能运行提供安全的沙盒虚拟环境。技能文件夹就像虚拟机里的目录，Claude 可以通过 bash 命令读取和执行。

三级加载：

  1. 一级：元数据，始终加载——SKILL.md 头部的名称和描述字段，启动时注入系统提示，通常只要几十个 token
  2. 二级：说明文档，技能触发时加载——SKILL.md 本身包含具体指令和示例，大约几千 token
  3. 三级：资源与脚本，按需加载——附加的 .md 文件、模板、数据库模式、可执行脚本，仅在被调用时才读取或执行

值得注意的一点：代码脚本通过 bash 调用，只把执行结果返回给 Claude，脚本本身的代码不会进入上下文。这让技能可以包含大量参考资料而不消耗上下文长度。

一个 Skill 的解剖：

与 Function Calling / MCP 的比较：

  • MCP 其实就是把 function calling 这类东西做了规范化处理。以前的 function calling 每家实现都不一样，都是 API 工具供大模型调用；MCP 相当于用一个统一协议来管理这些工具
  • Skills 是技能包，指导你如何使用这些技能、以及用到了哪些工具。它是一种更高的抽象，可以支撑企业内部业务知识库

三方对比速查

概念 层级 解决的问题
Function Call 最小单元 模型如何表达「我要调某个函数」
MCP 通信协议 工具如何被统一地发现、连接与调用
Skills 能力封装 复杂任务的知识与流程如何按需组织

五、上下文工程实战：从一份客户端 Agent 源码里学到的

这段是我觉得整份笔记里最有价值的部分。下面这些设计思路来自对 Claude 客户端 Agent 代码的分析。

Agent 循环

整体思想和 ReAct 一样朴素，核心就是这么一个 while(true)：

// query.ts
async function* queryLoop(params: QueryParams, consumedCommandUuids: string[]) {
  let state: State = {
    messages: params.messages,
    toolUseContext: params.toolUseContext,
    autoCompactTracking: undefined,
    maxOutputTokensRecoveryCount: 0,
    hasAttemptedReactiveCompact: false,
    turnCount: 1,
    // ...
  }

  while (true) {
    // 1. 上下文压缩（防止 token 爆炸）
    // 2. 调用大模型，流式获取响应
    // 3. 解析模型返回的工具调用
    // 4. 执行工具，获取结果
    // 5. 把结果追加到对话历史
    // 6. 如果没有新的工具调用，结束；否则继续循环
  }
}

每次循环通过 queryModel 函数和大模型沟通，负责发送请求、接收 SSE 流式输出、累计 token 用量。模型返回结果里如果包含 tool_use 类型的内容，说明还要继续干，循环接着转；没有 tool_use 了就结束。

源码注释里还有一段被称为「巫师守则」的思考块规则，写得挺有意思：

/**

工具设计：fail-closed 的默认值

Claude Code 内置了 40 多个工具，全部在 getAllBaseTools() 里注册：

// tools.ts — 工具注册文件
export function getAllBaseTools(): Tools {
  return [
    AgentTool,         // 子 Agent 生成
    TaskOutputTool,    // 任务输出
    BashTool,          // 执行终端命令
    ...(hasEmbeddedSearchTools() ? [] : [GlobTool, GrepTool]),
    FileReadTool,      // 读文件
    FileEditTool,      // 编辑文件
    FileWriteTool,     // 写文件
    NotebookEditTool,  // 编辑 Notebook
    WebFetchTool,      // 网络请求
    WebSearchTool,     // 网络搜索
    TodoWriteTool,     // 待办事项
    SkillTool,         // 技能调用
    EnterPlanModeTool, // 进入规划模式
    // ... 还有几十个，根据环境和 Feature Flag 动态加载
  ]
}

每个工具通过 buildTool 工厂函数创建，里面有个很巧妙的默认值设计：

// Defaults (fail-closed where it matters):
// - isConcurrencySafe → false (assume not safe)
// - isReadOnly → false (assume writes)
// - isDestructive → false
// - toAutoClassifierInput → '' (skip classifier)
const TOOL_DEFAULTS = {
  isEnabled: () => true,
  isConcurrencySafe: (_input?: unknown) => false,
  isReadOnly: (_input?: unknown) => false,
  isDestructive: (_input?: unknown) => false,
  toAutoClassifierInput: () => '',
}

isConcurrencySafe 和 isReadOnly 都默认 false——如果某个工具的开发者忘了声明「我只是读个文件，不会改东西」，系统就自动把它当危险操作处理，不让它并发执行。

这种思路叫 fail-closed（失败时关闭），像公司门禁：你没刷卡默认进不去。反过来 fail-open 就像小区大门，谁来都让进。

读写分离的并发编排

工具执行编排里做了一套读写分离机制。默认最多 10 个工具并发，核心分批逻辑：

// services/tools/toolOrchestration.ts
function partitionToolCalls(toolUseMessages, toolUseContext): Batch[] {
  return toolUseMessages.reduce((acc, toolUse) => {
    const tool = findToolByName(toolUseContext.options.tools, toolUse.name)
    const parsedInput = tool?.inputSchema.safeParse(toolUse.input)

    const isConcurrencySafe = parsedInput?.success
      ? (() => {
          try {
            return Boolean(tool?.isConcurrencySafe(parsedInput.data))
          } catch {
            return false  // 抛异常也当不安全，又是 fail-closed
          }
        })()
      : false  // 解析失败也当不安全

    if (isConcurrencySafe && acc[acc.length - 1]?.isConcurrencySafe) {
      acc[acc.length - 1].blocks.push(toolUse)  // 合并到并发批次
    } else {
      acc.push({ isConcurrencySafe, blocks: [toolUse] })  // 新开批次
    }
    return acc
  }, [])
}

连续几个只读工具可以一起跑，但一旦遇到写操作就得排队等前面完成。注意那个 try-catch——如果判断方法本身抛异常，也直接当不安全处理。

并发执行产生的上下文修改不会立刻生效，而是先排队，等一个批次全部跑完再按顺序依次应用：

if (isConcurrencySafe) {
  const queuedContextModifiers = {}
  for await (const update of runToolsConcurrently(blocks, ...)) {
    if (update.contextModifier) {
      // 先排队，不立即应用
      queuedContextModifiers[toolUseID].push(modifyContext)
    }
  }
  // 全部跑完后，按工具调用顺序依次应用
  for (const block of blocks) {
    for (const modifier of queuedContextModifiers[block.id]) {
      currentContext = modifier(currentContext)
    }
  }
}

System Prompt 的缓存分裂

系统提示词被一个 DYNAMIC_BOUNDARY 标记切成上下两半：

export const SYSTEM_PROMPT_DYNAMIC_BOUNDARY = '__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__'

sections = [
  // ...静态部分：角色定义、行为规范、工具说明、语气要求等
  // === BOUNDARY MARKER - DO NOT MOVE OR REMOVE ===
  ...(shouldUseGlobalCacheScope() ? [SYSTEM_PROMPT_DYNAMIC_BOUNDARY] : []),
  // --- Dynamic content (registry-managed) ---
  ...resolvedDynamicSections,
  // 动态部分：当前时间、git 状态、CLAUDE.md 配置、MCP 工具等
]

上面静态部分全球几百万用户共享同一份缓存，下面动态部分每个用户各不相同、独立加载。 这一刀下去，缓存命中率能高出一大截。

内容检索：不用 RAG，用 Grep

不管搜记忆文件还是搜历史对话，用的都是最朴素的文本搜索：

# memdir/memdir.ts — 记忆搜索指令
const memSearch = `grep -rn "<search term>" ${autoMemDir} --include="*.md"`
const transcriptSearch = `grep -rn "<search term>" ${projectDir}/ --include="*.jsonl"`

让 AI 自己决定搜什么、怎么搜，效果反而远远好于 RAG。 这点挺反直觉的，但在代码这种结构化、精确匹配为主的场景下确实成立。

三层记忆架构

这是我认为整份源码里设计最精妙的部分，也是 Context Engineering 领域最值得学的案例。

第一层：MEMORY.md（热数据，常驻加载）

MEMORY.md 就像一本书的目录，每次对话都会加载到上下文里。

export const ENTRYPOINT_NAME = 'MEMORY.md'
export const MAX_ENTRYPOINT_LINES = 200
// ~125 chars/line at 200 lines. At p97 today; catches long-line indexes that
// slip past the line cap (p100 observed: 197KB under 200 lines).
export const MAX_ENTRYPOINT_BYTES = 25_000

超限时怎么截断也有讲究：

export function truncateEntrypointContent(raw: string): EntrypointTruncation {
  // 先按行数截断
  let truncated = wasLineTruncated
    ? contentLines.slice(0, MAX_ENTRYPOINT_LINES).join('\n')
    : trimmed

  // 再按字节数截断，在最后一个换行符处切，避免截断到一半
  if (truncated.length > MAX_ENTRYPOINT_BYTES) {
    const cutAt = truncated.lastIndexOf('\n', MAX_ENTRYPOINT_BYTES)
    truncated = truncated.slice(0, cutAt > 0 ? cutAt : MAX_ENTRYPOINT_BYTES)
  }

  // 截断后追加 WARNING，让 AI 知道这个文件没加载完
  return {
    content: truncated +
      `\n\n> WARNING: ${ENTRYPOINT_NAME} is ${reason}. Only part of it was loaded.`,
  }
}

最后追加 WARNING 这个细节很关键——让模型知道自己看到的是残缺信息，避免它拿半截目录去做决策。

第二层：话题文件（温数据，按需加载）

编码偏好、项目架构约定、踩过的坑，都存在单独的话题文件里，比如 user_role.md、feedback_testing.md。

新对话开始时，用 Sonnet 小模型挑选最多 5 个跟当前对话相关的文件加载：

const SELECT_MEMORIES_SYSTEM_PROMPT = `You are selecting memories that will be
useful to Claude Code as it processes a user's query.
Return a list of filenames for the memories that will clearly be useful (up to 5).
- If a list of recently-used tools is provided, do not select memories that are
  usage reference or API documentation for those tools (Claude Code is already
  exercising them). DO still select memories containing warnings, gotchas, or
  known issues about those tools — active use is exactly when those matter.`

最后那条规则是 punchline：如果某个工具正在被使用，就不加载它的使用文档（你都在用了说明你会用），但一定要加载它的已知问题和坑。

另外——它从来不记忆代码，因为代码会发生变化。

第三层：历史对话（冷数据，Grep 搜索）

更早的历史对话存成 .jsonl 文件，需要时用 Grep 搜关键词。

五级上下文压缩

上下文爆炸是长会话绕不开的问题，这里设计了五级策略，像漏斗一样层层过滤：

  1. Snip 剪裁——最轻的一刀，把旧的工具调用结果只保留结构、不保留内容
  2. Microcompact 微压缩——把体积大的工具执行结果卸载到缓存里。注意是卸载而不是丢掉，因为子智能体后续可能还需要
  3. Context Collapse 折叠——对中间的对话做折叠摘要，只保留关键信息
  4. Autocompact 自动压缩——当上下文占用超过阈值时，触发全量摘要压缩
  5. Reactive Compact 应急压缩——最后兜底，当 API 返回 413「提示词太长」时紧急触发

六、Transformer 与推理侧高频问题

Transformer 为什么比 RNN 更适合做大模型？

核心在于并行计算能力和长程依赖建模效率的巨大差异。

  • RNN 必须按时间步顺序处理，每个 token 的计算依赖前一个的隐藏状态。这种串行特性导致训练无法并行化，处理长文本时梯度传播路径过长容易梯度消失。即使 LSTM 缓解了这个问题，本质的串行瓶颈依然存在
  • Transformer 通过自注意力直接计算任意两个位置的关联，所有 token 可以同时处理，充分利用 GPU 并行能力。更重要的是任意两个 token 间都是一步直连，不存在梯度衰减问题，能有效学习文档级别的长距离依赖

架构与自注意力

Transformer 基于 Encoder-Decoder 结构，完全依靠自注意力替代 RNN 序列建模，支持并行计算。但它本身不能利用单词的顺序信息，因此需要在输入中添加位置编码。大致分为输入层、编码层、解码层、输出层。

大体流程：

  1. 获取每个单词的表示向量 X——由单词 Embedding 和位置 Embedding 相加得到

  1. 将表示向量矩阵传入 Encoder，经过 6 个 Encoder block 后得到编码信息矩阵 C。单词向量矩阵用 X(n×d) 表示，n 是单词个数，d 是向量维度（论文中 d=512）。每个 Encoder block 输出的矩阵维度与输入完全一致

  1. 将 C 传递到 Decoder，Decoder 依次根据已翻译的单词 1~i 翻译下一个单词 i+1。翻译到 i+1 时需要通过 Mask 操作遮盖住 i+1 之后的单词
  2. Decoder 先输入翻译开始符 <Begin> 预测第一个单词，再输入 <Begin> 和已预测单词预测下一个，以此类推

三类架构：面试精简版

  • Encoder-only——仅用编码器，双向注意力（可看到全文）。优点是双向上下文理解强、适合理解/分类/抽取任务、训练稳定推理快；缺点是不擅长生成。典型模型：BERT、RoBERTa、ALBERT、DistilBERT。适用：文本分类、情感分析、NER、语义相似度、抽取式摘要
  • Decoder-only——仅用解码器，因果自注意力（只能看当前及之前 token）。优点是生成能力极强、结构简单易扩展、适合续写对话创作；缺点是对理解类任务精度不如 encoder-only、推理逐 token 生成速度慢。典型模型：GPT 系列、LLaMA、Qwen、Mistral、Falcon。适用：对话、文案生成、代码生成、开放问答
  • Encoder-Decoder——适合翻译这类既要理解又要生成的任务

KV Cache 是什么？

KV Cache 是 Transformer 在自回归生成时，用来存储每个 token 的 Key 和 Value 矩阵的缓存机制。

推理时模型每次只生成一个新 token，但 Attention 计算需要当前 token 的 Query 与所有历史 token 的 Key 做点积得到注意力分数，再用这些分数加权所有历史 token 的 Value。如果不用缓存，每生成一个新 token 都要把之前所有 token 重新输入模型计算一遍 K 和 V——造成大量重复计算，因为历史 token 的 K、V 矩阵其实不会改变。

首字延迟为什么高？

首字延迟高，主要是第一次生成前的初始化与计算开销远大于后续逐字生成：

  • KV Cache 未初始化——首字需要为整个上下文分配显存、构建 KV Cache；后续生成直接复用缓存，只需计算最后一个 token
  • 上下文计算量差异极大——首字要对全部输入 tokens 做完整的 Attention + FFN 计算；后续只算新增的单个 token

大模型为什么强？是不是过拟合？

不是过拟合，恰恰相反，是强泛化的结果。

  • 参数规模足够大，能拟合极其复杂的语言规律、知识分布和世界知识
  • 海量高质量文本预训练，从互联网、书籍、代码中学习通用语义、逻辑、常识和推理模式
  • Transformer 全局注意力能捕捉长距离依赖
  • 涌现能力 Emergent Ability——规模达到阈值后，突然出现推理、代码、对话、少样本学习等复杂能力
  • Decoder-only 架构 + 自回归生成 + 高效训练框架，让泛化能力极强

补充一点：我以前对这个问题的理解一直是错的，总往过拟合上想。正确的直觉是——参数巨大所以能拟合各种各样的世界规律，再加上全局注意力 + decoder-only + 预训练。

一次完整生成发生了什么？

  1. 用户输入 → tokenizer 分词 → token 序列
  2. 输入 embedding + 位置编码 → 送入 transformer
  3. 每一层做多头注意力 + FFN，因果掩码确保只看前文（decoder-only）
  4. 输出层映射到词表概率分布
  5. 通过采样（greedy / top-k / top-p）选下一个 token
  6. 循环自回归生成，直到结束符
  7. token 转回文本返回

Transformer 为什么对首尾字符比较敏感？

这个问题是我面试时随口说了一句被追问原因的，自己猜的答案没想到是对的。系统梳理一下：

  • 位置编码——开头和结尾是位置分布中最独特的编码（结尾位置编码后有折回现象）。我觉得本质是：所有 token 都会对开头做 attention，而结尾就是结束了
  • 注意力分布偏好——更容易关注开头，因为开头一般是一段话的主题和主语，是上下文的锚点，同时第一个 token 会被后续所有 token 注意到；也更容易关注结尾，因为 decoder 结构专注当前和附近的 token，而结尾通常是结论这类关键语句

prompt engineering 里很多关键信息放在头尾，正是参考了这个特点。

温度参数

温度参数控制模型在生成下一个词时对概率分布的调整程度，决定输出更确定还是更随机。

数学上，温度通过调整 softmax 实现——分子部分变成 e^(Z/T)（T 为温度，Z 是模型输出的原始 logits）：

  • 低温度——高概率词概率更高、低概率词更低，模型倾向选概率最高的词，生成更保守、可预测、连贯性强
  • 高温度——各词概率差异减小，随机性变大，生成更有创造性、多样性，但可能出现不连贯内容

Agent 如何降低幻觉？

  • 外部知识库——用 RAG 等手段，或者外挂一个知识图谱
  • 强 prompt 约束
