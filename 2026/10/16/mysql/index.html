一、索引

什么是索引，有什么优缺点

索引是一种特殊的文件（InnoDB 数据表上的索引是表空间的一个部分）。

优点：

  • 大大加快数据检索的速度
  • 将随机 I/O 变成顺序 I/O（因为 B+ 树的叶子节点是连接在一起的）
  • 加速表与表之间的连接

缺点：

  • 从空间角度，建立索引需要占用物理空间
  • 从时间角度，创建和维护索引都需要花费时间——比如对数据进行增删改时都需要维护索引

索引的数据结构

主要有 B+ 树和哈希表两种，对应 B+ 树索引和哈希索引。InnoDB 引擎的索引类型有 B+ 树索引和哈希索引，默认是 B+ 树索引。

B+ 树索引

所有的记录节点都是按照键值大小的顺序放在叶子节点上。

因为 B+ 树（多路搜索树，时间复杂度固定为 O(log n)，很好地利用了局部性原理）具有有序性，并且所有数据都存放在叶子节点，所以查找效率非常高，并且支持排序和范围查找。

B+ 树的索引又可以分为主索引和辅助索引：

  • 主索引即聚簇索引，是以主键作为 B+ 树索引的键值所构成的索引，叶子节点存储着完整的数据记录
  • 辅助索引即非聚簇索引，是以非主键的列作为 B+ 树索引的键值所构成的索引，叶子节点存储着主键值

所以使用非聚簇索引查询时，会先找到主键值，然后再根据聚簇索引找到主键对应的数据域。

上图中字母为数据的非主键列值。假设要查询该列值为 B 的信息，则需要先找到主键 7，再到聚簇索引中查询主键 7 所对应的数据域。

哈希索引

基于哈希表实现。对于每一行数据，存储引擎会对索引列通过哈希算法计算得到哈希码（哈希算法要尽量保证不同的列值算出的哈希码不同），将哈希码作为哈希表的 key，将指向数据行的指针作为 value。

这样查找一个数据的时间复杂度就是 O(1)，一般多用于精确查找。

为什么用 B+ 树而不是 B 树（重点）

  • B 树的内部节点和叶子节点均存放键和值，而 B+ 树的内部节点只有键没有值，叶子节点存放所有的键和值
  • B+ 树的叶子节点通过指针相连，方便顺序检索

四点关键差异：

  1. B 树适用于随机检索，B+ 树适用于随机检索和顺序检索
  2. B+ 树空间利用率更高——B 树每个节点要存储键和值，而 B+ 树的内部节点只存储键，这样一个节点就可以存储更多的索引，从而使树的高度变低，减少 I/O 次数，数据检索速度更快
  3. B+ 树叶子节点连接在一起，范围查找、顺序查找更方便
  4. B+ 树性能更稳定——B+ 树每次查询都是从根节点到叶子节点；而 B 树要查询的值可能不在叶子节点，在内部节点就已经找到了

为什么用 B+ 树而不是 Redis 的跳表（重点）

  • B+ 树是多叉树，每个节点是一个 16K 的数据页，能存放较多索引信息，所以扇出很高。三层左右就可以存储 2kw 左右的数据。也就是说查询一次数据，如果这些数据页都在磁盘里，最多需要三次磁盘 IO
  • 跳表是链表结构，一条数据一个节点。如果最底层要存放 2kw 数据，且每次查询都要达到二分查找效果（2kw 约在 2 的 24 次方），那么跳表高度大概在 24 层左右。最坏情况下这 24 层数据会分散在不同的数据页里，查一次数据会经历 24 次磁盘 IO
  • 因此存放同样量级的数据，B+ 树的高度比跳表少——放到 MySQL 上就是磁盘 IO 次数更少，查询更快。而 Redis 数据都在内存里，不需要这些；用 B+ 树的话平衡反而成了负担
  • 但针对写操作，B+ 树需要拆分合并索引数据页，跳表则独立插入，并根据随机函数确定层数，没有旋转和维持平衡的开销，所以跳表的写入性能比 B+ 树好

聚簇索引与非聚簇索引

最主要的区别是数据和索引是否分开存储：

  • 聚簇索引——将数据和索引放到一起存储，索引结构的叶子节点保留了数据行。一个表只能存在一个聚簇索引。利用主键创建的索引为主索引，也是聚簇索引
  • 非聚簇索引——将数据和索引分开存储，索引叶子节点存储的是指向数据行的地址。在主索引之上创建的索引为辅助索引，也是非聚簇索引

为什么说辅助索引是在主索引之上创建的呢？因为辅助索引中的叶子节点存储的是主键。

非聚簇索引一定会回表吗？（出现索引覆盖就不需要）

答案是不一定，这里涉及索引覆盖的问题——如果查询的数据在辅助索引上完全能获取到，便不需要回表查询。

举例：有一张表存储个人信息，包括 id、name、age 等字段。假设聚簇索引以 ID 为键值构建，非聚簇索引以 name 为键值构建：

-- 不需要回表：通过非聚簇索引已经能全部检索出数据，这就是索引覆盖
SELECT id, name FROM user WHERE name = 'zhangsan';

-- 需要回表：通过非聚簇索引不能检索出 age 的值
SELECT id, name, age FROM user WHERE name = 'zhangsan';

索引的使用场景

  • 数据比较多的时候，中大型的表建立索引
  • 如果表的增删改非常多、查询需求非常少，那就没必要建索引了，因为维护索引也需要代价
  • 一般不会出现在 where 条件中的字段就没有必要建索引
  • 多个字段经常被查询的话，可以考虑联合索引
  • 字段多且字段值没有重复的时候，考虑唯一索引
  • 字段多且有重复的时候，考虑普通索引

索引设计原则

  • 最适合索引的列是在 where 后面出现的列，或者连接（Join）子句中指定的列，而不是出现在 SELECT 关键字后面的选择列表中的列
  • 索引列的区分度越高，索引的效果越好
  • 尽量利用最左匹配
  • 尽量使用短索引，减少磁盘 IO 操作

什么是前缀索引

前缀索引是指对文本或字符串的前几个字符建立索引，这样索引的长度更短，查询速度更快。

如何对索引进行优化

最关键的还是要符合索引的设计原则和应用场景。除此之外还可以从两方面考虑：

  • 将区分度最高的索引放在前面
  • **尽量少使用 select ***——因为需要回表查询，有大量时间开销

最左匹配原则

从最左边为起点开始连续匹配，遇到范围查询（<、>、between、like）会停止匹配。

最左匹配原则一定是在复合索引上——B+ 树存储索引的特点是按照索引列的顺序进行排序和存储。因此当查询条件从最左列开始时，数据库可以快速定位到满足条件的数据范围，然后进行高效的查找和扫描。利用复合索引查询时不符合最左匹配的话，索引会失效。

CREATE INDEX idx_name_age_department_id ON employees(name, age, department_id);

上面的语句建立的组合索引，实际上相当于建立了三个索引：[name, age, department_id]、[name, age]、[name]。

满足最左匹配的情况：

SELECT * FROM employees WHERE name = 'Alice' AND age = 25 AND department_id = 1;
SELECT * FROM employees WHERE name = 'Alice' AND age = 25;

不满足的情况：

SELECT * FROM employees WHERE age = 25 AND department_id = 1;

单列索引和组合索引

  • 单列索引——一个索引只包含单个列，一个表可以有多个单列索引（唯一索引、普通索引）
  • 组合索引（也叫复合索引、联合索引）——一个索引包含多个列

索引什么情况下会失效（重点）

  • 不符合最左匹配原则
  • 条件中有 or
  • 在索引上进行计算会导致索引失效
  • 在索引中使用函数会导致索引失效
  • 在索引的类型上进行数据类型的隐式转换

二、事务

什么是数据库事务

事务是一个不可分割的数据库操作序列，也是数据库并发控制的基本单位，其执行结果必须使数据库从一种一致性状态变到另一种一致性状态，确保数据的最终一致性。

事务的四个特征（ACID）

  • 原子性（Atomicity）——事务是数据库的逻辑工作单位，事务中包含的各操作要么都做，要么都不做
  • 一致性（Consistency）——事务执行的结果必须是使数据库从一个一致性状态变到另一个一致性状态。当数据库只包含成功事务提交的结果时，就说数据库处于一致性状态。如果数据库系统运行中发生故障，有些事务尚未完成就被迫中断，这些未完成事务对数据库所做的修改有一部分已写入物理数据库，这时数据库就处于一种不正确（不一致）的状态
  • 隔离性（Isolation）——一个事务的执行不能被其它事务干扰，即一个事务内部的操作及使用的数据对其它并发事务是隔离的
  • 持久性（Durability）——也称永久性，指一个事务一旦提交，它对数据库中数据的改变就应该是永久性的，接下来的其它操作或故障不应该对其执行结果有任何影响

MySQL 的四种隔离级别

  • Read Uncommitted（读取未提交内容）——所有事务都可以看到其他未提交事务的执行结果。本隔离级别很少用于实际应用，因为性能也不比其他级别好多少。读取未提交的数据，也被称为脏读（Dirty Read）
  • Read Committed（读取提交内容）——大多数数据库系统的默认隔离级别（但不是 MySQL 默认的）。它满足了隔离的简单定义：一个事务只能看见已经提交事务所做的改变。这个级别支持所谓的不可重复读（Nonrepeatable Read）——因为同一事务的其他实例在该实例处理期间可能会有新的 commit，所以同一 select 可能返回不同结果
  • Repeatable Read（可重读）——MySQL 的默认事务隔离机制，它确保同一事务的多个实例在并发读取数据时会看到同样的数据行。不过理论上这会导致另一个棘手的问题：幻读（Phantom Read）
  • Serializable（可串行化）——通过强制事务排序，使之不可能相互冲突，从而解决幻读问题。简言之，它是在每个读的数据行上加上共享锁。在这个级别可能导致大量的超时现象和锁竞争

隔离级别与三种读问题的对应关系：

隔离级别 脏读 不可重复读 幻读
READ-UNCOMMITTED √ √ √
READ-COMMITTED × √ √
REPEATABLE-READ × × √
SERIALIZABLE × × ×

InnoDB 存储引擎在分布式事务的情况下，一般会用到 SERIALIZABLE（可串行化）隔离级别。

脏读 / 不可重复读 / 幻读

  1. 脏读——事务 A 读取了事务 B 更新的数据，然后 B 回滚操作，那么 A 读取到的数据是脏数据
  2. 不可重复读——事务 A 多次读取同一数据，事务 B 在事务 A 多次读取的过程中对数据作了更新并提交，导致事务 A 多次读取同一数据时结果不一致
  3. 幻读——系统管理员 A 将数据库中所有学生的成绩从具体分数改为 ABCDE 等级，但系统管理员 B 就在这个时候插入了一条具体分数的记录，当 A 改结束后发现还有一条记录没有改过来，就好像发生了幻觉一样

一句话区分：不可重复读侧重于修改，幻读侧重于新增或删除（多了或少了行），脏读是一个事务回滚影响另外一个事务。

事务的实现原理：redo log 与 undo log（重点）

事务是基于重做日志文件（redo log）和回滚日志（undo log）实现的。

  • 每提交一个事务，必须先将该事务的所有日志写入到重做日志文件进行持久化，数据库就可以通过重做日志来保证事务的原子性和持久性
  • 每当有修改事务时还会产生 undo log，如果需要回滚，则根据 undo log 的反向语句进行逻辑操作——比如 insert 一条记录就 delete 一条记录。undo log 主要实现数据库的一致性
  • redo log 不是随着事务的提交才写入的，而是在事务的执行过程中便开始写入

什么是 binlog

MySQL 的 binlog 是记录所有数据库表结构变更（如 CREATE、ALTER TABLE）以及表数据修改（INSERT、UPDATE、DELETE）的二进制日志。

binlog 不会记录 SELECT 和 SHOW 这类操作，因为这类操作对数据本身并没有修改（但你可以通过查询通用日志来查看 MySQL 执行过的所有语句）。

binlog 以事件形式记录，还包含语句所执行的消耗时间，是事务安全型的。主要目的是复制和恢复。

三种模式：

  • statement——基于 SQL 语句的模式。某些语句和函数如 UUID、LOAD DATA INFILE 等在复制过程可能导致数据不一致甚至出错
  • row——基于行的模式，记录的是行的变化，很安全。但 binlog 会比其他两种模式大很多，在一些大表中清除大量数据时会生成很多条语句，可能导致从库延迟变大
  • mixed——混合模式，根据语句来选用 statement 还是 row

事务中可以混合使用存储引擎吗

尽量不要在同一个事务中使用多种存储引擎——MySQL 服务器层不管理事务，事务是由下层的存储引擎实现的。

MySQL 如何实现事务隔离

事务隔离机制的实现基于锁机制和并发调度。

其中并发调度使用的是 MVCC（多版本并发控制），通过保存修改的旧版本信息来支持并发一致性读和回滚等特性。

MySQL 在可重复读级别解决幻读问题，是通过行锁和间隙锁的组合 Next-Key Lock 实现的。

MVCC 及其实现原理（重点）

数据结构：对于 InnoDB，聚簇索引记录中包含 3 个隐藏的列：

  • ROW ID——隐藏的自增 ID。如果表没有主键，InnoDB 会自动按 ROW ID 产生一个聚集索引树
  • 事务 ID——记录最后一次修改该记录的事务 ID
  • 回滚指针——指向这条记录的上一个版本

上图为例：首先 insert 语句向表 t1 中插入一条数据，a 字段为 1，b 字段为 1，ROW ID 也为 1，事务 ID 假设为 1，回滚指针假设为 null。当执行 update t1 set b=666 where a=1 时，大致步骤如下：

  1. 数据库会先对满足 a=1 的行加排他锁
  2. 然后将原记录复制到 undo 表空间中
  3. 修改 b 字段的值为 666，修改事务 ID 为 2
  4. 并通过隐藏的回滚指针指向 undo log 中的历史记录
  5. 事务提交，释放前面对满足 a=1 的行所加的排他锁

MVCC 原理：InnoDB 每一行数据都有一个隐藏的回滚指针，用于指向该行修改前的最后一个历史版本，这个历史版本存放在 undo log 中。如果要执行更新操作，会将原记录放入 undo log，并通过隐藏的回滚指针指向 undo log 中的原记录。其它事务此时需要查询时，就是查询 undo log 中这行数据的最后一个历史版本。

MVCC 最大的好处是读不加锁、读写不冲突，极大地增加了 MySQL 的并发性。通过 MVCC 保证了事务 ACID 中的 I（隔离性）特性。

三、锁

为什么要加锁

当多个用户并发地存取数据时，数据库中就会产生多个事务同时存取同一数据的情况。若对并发操作不加控制，就可能会读取和存储不正确的数据，破坏数据库的一致性。

按锁的粒度分

在关系型数据库中，可以按锁的粒度分为行级锁（InnoDB 引擎）、表级锁（MyISAM 引擎）和页级锁（BDB 引擎）。

行级锁

  • 锁定粒度最细，表示只针对当前操作的行进行加锁，能大大减少数据库操作的冲突。行级锁分为共享锁和排他锁
  • 开销大、加锁慢；会出现死锁；锁定粒度最小，发生锁冲突的概率最低，并发度最高

表级锁

  • 锁定粒度最大，表示对当前操作的整张表加锁，实现简单、资源消耗较少，被大部分 MySQL 引擎支持。最常使用的 MyISAM 与 InnoDB 都支持表级锁定。分为表共享读锁（共享锁）与表独占写锁（排他锁）
  • 开销小、加锁快；不会出现死锁；锁定粒度大，发出锁冲突的概率最高，并发度最低

页级锁

  • 锁定粒度介于行级锁和表级锁中间。表级锁速度快但冲突多，行级冲突少但速度慢，所以取了折衷的页级，一次锁定相邻的一组记录。BDB 支持页级锁
  • 开销和加锁时间介于表锁和行锁之间；会出现死锁；并发度一般

从锁的类别分

  • 共享锁（S）——又叫读锁。当用户要进行数据读取时，对数据加上共享锁。共享锁可以同时加上多个
  • 排他锁（X）——又叫写锁。当用户要进行数据写入时，对数据加上排他锁。排他锁只可以加一个，它和其他的排他锁、共享锁都相斥

乐观锁和悲观锁

数据库管理系统（DBMS）中并发控制的任务，是确保在多个事务同时存取数据库中同一数据时，不破坏事务的隔离性、统一性以及数据库的统一性。乐观并发控制和悲观并发控制是并发控制主要采用的技术手段。

  • 悲观锁——假定会发生并发冲突，屏蔽一切可能违反数据完整性的操作。在查询完数据的时候就把事务锁起来，直到提交事务。实现方式：使用数据库中的锁机制
  • 乐观锁——假设不会发生并发冲突，只在提交操作时检查是否违反数据完整性。在修改数据的时候把事务锁起来，通过 version 的方式来进行锁定。实现方式：一般会使用版本号机制或 CAS 算法

使用场景：两种锁各有优缺点，不可认为一种好于另一种。

  • 乐观锁适用于写比较少的情况（多读场景）——冲突真的很少发生的时候，可以省去锁的开销，加大系统的整体吞吐量
  • 多写场景下用悲观锁更合适——如果经常产生冲突，会导致上层应用不断 retry，反倒降低性能

间隙锁

  • 间隙锁是对索引记录之间间隙的一种锁定，而不是锁定具体的记录。目的是防止其他事务在该间隙范围内插入新的数据，从而防止幻读，确保事务的隔离性
  • 当执行范围查询（如 SELECT ... WHERE column BETWEEN A AND B FOR UPDATE）时，InnoDB 会锁定查询范围内的所有记录以及这些记录之间的间隙

    例如表 t 中已有记录 (1, 2, 4, 5)，事务 A 执行 SELECT * FROM t WHERE id BETWEEN 2 AND 4 FOR UPDATE，InnoDB 会锁定记录 2 和 4 之间的间隙，即锁定范围 (2,4)。在事务 A 提交之前，事务 B 不能在该间隙内插入新记录（如插入 id=3 的记录）

  • 间隙锁仅在可重复读（REPEATABLE READ）隔离级别下才有效

间隙锁的加锁规则

  • 规则 1——加锁的基本单位是 Next-Key Lock，左开右闭区间
  • 规则 2——查找过程中访问到的对象才会加锁
  • 规则 3——唯一索引上的范围查询，会上锁到不满足条件的第一个值为止
  • 规则 4——唯一索引等值查询且记录存在，Next-Key Lock 退化为行锁
  • 规则 5——索引上的等值查询（唯一索引），给不存在的记录加锁时，优化为间隙锁
  • 规则 6——索引上的等值查询（非唯一普通索引），向右遍历时最后一个值不满足查询需求时，next-key lock 退化为间隙锁

InnoDB 的行锁是怎么实现的，有几类

InnoDB 是基于索引来完成行锁的。

SELECT * FROM tab_with_index WHERE id = 1 FOR UPDATE;

for update 可以根据条件完成行锁锁定，并且 id 是有索引键的列。如果 id 不是索引键，那么 InnoDB 将完成表锁，并发将无从谈起。

三类：

  • 记录锁（Record Lock）——属于单个行记录上的锁
  • 间隙锁（Gap Lock）——锁定一个范围，不包括记录本身
  • 临键锁（Next-Key Lock）——Record Lock + Gap Lock，锁定一个范围，包括记录本身，主要目的是用于解决幻读问题

意向锁有什么作用

  • 意向锁是表级锁，用于快速判断是否可以对某个表使用表锁，即判断表中的记录有没有行锁
  • 意向共享锁（IS 锁）——事务有意向对表中的某些记录加共享锁，加共享锁前必须先取得该表的 IS 锁
  • 意向排他锁（IX 锁）——事务有意向对表中的某些记录加排他锁，加排他锁之前必须先取得该表的 IX 锁

快照读与当前读的区别

  • 快照读（一致性非锁定读）——就是单纯的 SELECT 语句，快照即每行记录的历史版本。读取操作不会去等待记录上 X 锁的释放，而是会去读取行的一个快照。只有在 RC（读取已提交）和 RR（可重读）隔离级别下，InnoDB 才会使用一致性非锁定读。适合对数据一致性要求不是特别高、且追求极致性能的业务场景
  • 当前读（一致性锁定读）——就是给行记录加 X 锁或 S 锁

当前读的常见 SQL 语句类型：

SELECT ... FOR UPDATE              -- 对读的记录加一个 X 锁
SELECT ... LOCK IN SHARE MODE      -- 对读的记录加一个 S 锁
SELECT ... FOR SHARE               -- 对读的记录加一个 S 锁
INSERT...
UPDATE...
DELETE...                          -- 对修改的记录加一个 X 锁

两个典型场景：

  • 查看自己的订单列表——用快照读（SELECT * FROM orders WHERE user_id = ?）。用户不关心刚刚提交的订单是否立刻出现在列表里，且高并发下性能更好
  • 支付订单——用当前读（SELECT * FROM orders WHERE order_no = ? FOR UPDATE）。支付流程必须基于订单的最新状态（是否已支付、是否取消）来做决策，并锁定该订单以防止重复支付

什么是死锁，怎么解决

死锁是指两个或多个事务在同一资源上相互占用，并请求锁定对方的资源，从而导致恶性循环的现象（锁交叉）。

常见的解决方法：

  1. 如果不同程序会并发存取多个表，尽量约定以相同的顺序访问表，可以大大降低死锁机会
  2. 在同一个事务中，尽可能做到一次锁定所需要的所有资源，减少死锁产生概率
  3. 对于非常容易产生死锁的业务部分，可以尝试升级锁的颗粒度，通过表级锁定来减少死锁产生的概率

隔离级别与锁的关系

  • Read Uncommitted 级别下，读取数据不需要加共享锁，这样就不会跟被修改数据上的排他锁冲突
  • Read Committed 级别下，读操作需要加共享锁，但是在语句执行完后释放共享锁
  • Repeatable Read 级别下，读操作需要加共享锁，但在事务提交之前并不释放，也就是必须等待事务执行完毕以后才释放
  • SERIALIZABLE 是限制性最强的隔离级别，因为该级别锁定整个范围的键，并一直持有锁直到事务完成

优化锁方面的建议

  • 使用较低的隔离级别（级别越低，加的锁越少，降低冲突）
  • 设计索引，尽量使用索引去访问数据，加锁更加精确，从而减少锁冲突
  • 选择合理的事务大小。给记录显式加锁时，最好一次性请求足够级别的锁——比如修改数据的话最好直接申请排他锁，而不是先申请共享锁、修改时再申请排他锁，这样会导致死锁
  • 尽量使用相等条件访问数据，这样可以避免间隙锁对并发插入的影响
  • 不要申请超过实际需要的锁级别
  • 不同的程序访问一组表的时候，应尽量约定一个相同的顺序访问各表；对于一个表而言，尽可能固定顺序获取表中的行。这样大大减少死锁的机会

四、分库分表

为什么要分库分表

分表就是把一个表的数据放到多个表中，查询时就查一个表。比如按用户 id 分表，将一个用户的数据放在一个表中（单个表的数据过大，会影响查询的性能）。

分库——一个库一般我们经验而言，最多支撑到并发 2000，一定要扩容了，而且一个健康的单库并发值最好保持在每秒 1000 左右，不要太大。

一个参考经验：单表行数小于 1000w 且数据库有合适的索引、加上 Redis 缓存，一般不需要分表。

垂直拆分与水平拆分

  • 水平拆分——把一个表的数据弄到多个库的多个表里去，但每个库的表结构都一样，只不过每个库表放的数据不同，所有库表的数据加起来就是全部数据。意义是将数据均匀放到更多的库里，用多个库来抗更高的并发，同时用多个库的存储容量来扩容
  • 垂直拆分——把一个有很多字段的表拆分成多个表，或者放到多个库上。每个库表的结构都不一样，每个库表都包含部分字段。一般来说，会将访问频率高的字段放到一个表里，访问频率低的字段放到另外一个表里。因为数据库是有缓存的，访问频率高的行字段越少，就可以在缓存里缓存更多的行，性能就越好。这个一般在表层面做得较多

两种分库分表的方式

  • 按 range 分——每个库一段连续的数据，一般是按时间范围来分。好处是扩容简单（预备好每个月一个库，到了新月份自然就写新库了）；缺点是容易产生热点问题，大量流量都打在最新的数据上。实际生产用 range 要看场景
  • 按 hash 分——按某个字段 hash 一下均匀分散，较为常用。好处是可以平均分配每个库的数据量和请求压力；坏处是扩容比较麻烦，会有一个数据迁移的过程，之前的数据需要重新计算 hash 值重新分配到不同的库或表

五、读写分离与主从同步

什么是 MySQL 主从同步

主从同步使得数据可以从一个数据库服务器复制到其他服务器上。复制数据时，一个服务器充当主服务器（master），其余的充当从服务器（slave）。

因为复制是异步进行的，所以从服务器不需要一直连接着主服务器，甚至可以通过拨号断断续续地连接。通过配置文件，可以指定复制所有的数据库、某个数据库，甚至是某个数据库上的某个表。

为什么要做主从同步

  • 提高性能——在主服务器上执行写入和更新，在从服务器上对外提供读功能，可以动态调整从服务器的数量，从而调整整个数据库的性能
  • 提高数据安全——数据已复制到从服务器，从服务器可以终止复制进程，所以可以在从服务器上备份而不破坏主服务器相应数据
  • 在主服务器上生成实时数据，在从服务器上分析这些数据，从而提高主服务器性能
  • 数据备份——主从能很好地解决这个问题，不仅备份及时，而且可以多地备份

主从复制的流程和原理

基本原理流程，是3 个线程以及之间的关联：

  • 主：binlog 线程——记录下所有改变了数据库数据的语句，放进 master 上的 binlog 中
  • 从：io 线程——在使用 start slave 之后，负责从 master 上拉取 binlog 内容，放进自己的 relay log 中
  • 从：sql 执行线程——执行 relay log 中的语句

主从同步延时问题如何解决

MySQL 实际上有两个同步机制：一个是半同步复制，用来解决主库数据丢失问题；一个是并行复制，用来解决主从同步延时问题。

  • 半同步复制（semi-sync）——主库写入 binlog 日志之后，会强制立即将数据同步到从库，从库将日志写入自己本地的 relay log 之后会返回一个 ack 给主库，主库接收到至少一个从库的 ack 之后才会认为写操作完成了
  • 并行复制——从库开启多个线程，并行读取 relay log 中不同库的日志，然后并行重放不同库的日志，这是库级别的并行

六、MySQL 优化

如何定位及优化 SQL 语句的性能问题

  • 使用 EXPLAIN 分析查询计划——在查询语句前添加 EXPLAIN 关键字，可查看查询的执行计划，包括查询优化器如何选择表的连接顺序、如何选择索引等。根据输出结果，可以判断查询语句是否使用了索引、是否存在全表扫描等情况，从而发现性能问题所在
  • 检查慢查询日志——开启慢查询日志功能，通过设置 long_query_time 参数指定记录执行时间超过该值的 SQL 语句。分析慢查询日志可以找到执行时间较长的 SQL，从而确定需要优化的对象

EXPLAIN 关键字段速查：

字段 含义
type 访问类型。从差到好：ALL（全表扫描）→ index（索引扫描）→ range（范围扫描）→ ref（非唯一索引）→ eq_ref（唯一索引）→ const（常量）
key_len 实际索引的长度
Extra 额外信息，如 using index 表示索引覆盖

大表查询怎么优化（重点）

类似的问题：某个表有近千万数据，CRUD 比较慢，如何优化？分库分表了是怎么做的？分表分库了有什么问题？有用到中间件么？它们的原理知道么？

  • 限定数据的范围——务必禁止不带任何限制数据范围条件的查询语句。比如用户查询订单历史时，控制在一个月的范围内
  • 读写分离——经典的数据库拆分方案，主库负责写，从库负责读
  • 缓存——使用 Redis 缓存；另外对重量级、更新少的数据可以考虑
  • 通过分库分表进行优化——主要有垂直分表和水平分表
  • 加索引

慢查询怎么优化（重点）

首先要搞明白慢的原因是什么：是查询条件没有命中索引？是 load 了不需要的数据列？还是数据量太大？

  • 首先分析语句，看看是否 load 了额外的数据——可能是查询了多余的行并且抛弃掉了，也可能是加载了许多结果中并不需要的列。对语句进行分析以及重写
  • 分析语句的执行计划 EXPLAIN，获得其使用索引的情况，之后修改语句或者修改索引，使得语句尽可能命中索引
  • 如果对语句的优化已经无法进行，考虑表中的数据量是否太大，如果是的话可以进行横向或者纵向的分表

数据库结构优化

表的规范化程度越高，表和表之间的关系越多，需要连接查询的情况也就越多，性能也就越差。

  • 合理地加入冗余字段可以提高查询速度
  • 增加中间表——对于需要经常联合查询的表，可以建立中间表以提高查询效率
  • 如果有些字段的使用频率很低，将这些字段分离出来形成新表（垂直拆分）

如何优化关联查询

  • 确定 ON 或者 USING 子句中是否有索引
  • 确保 GROUP BY 和 ORDER BY 只有一个表中的列，这样 MySQL 才有可能使用索引

MySQL 数据库 CPU 飙升到 100% 怎么处理

  • 先找是什么原因导致的占用——先用 top 命令观察是不是 mysqld（MySQL 数据库服务器的核心守护进程，负责存储、查询执行、事务管理、用户认证等所有数据库操作）占用导致。如果不是，找出占用高的进程并进行相关处理
  • 如果是 mysqld 造成的——用 show processlist 看看里面跑的 session 情况，是不是有消耗资源的 SQL 在运行。找出消耗高的 SQL，看看执行计划是否准确、索引是否缺失，或者是不是数据量太大造成

从 MySQL 读取 100w 数据进行处理，应该怎么做

  • 流式查询——指的是查询成功后不是返回一个集合而是返回一个迭代器（游标），应用每次从迭代器取一条查询结果。好处是能够降低内存使用
  • 分页查询——分页查询的效率取决于表设计，如果设计得不好就无法执行高效的分页查询。用 limit（限定展示的数据）+ offset（跳过前面多少行）进行查询

七、SQL 基础

SQL 约束有哪些

  • 主键约束——主键为表中存在的一列或多列组合，能唯一标识表中的每一行。一个表只有一个主键，并且主键约束的列不能为空
  • 外键约束——用于在两个表之间建立关系，需要指定引用主表的哪一列。只有主表的主键可以被从表用作外键，被约束的从表的列可以不是主键，所以创建外键约束需要先定义主表的主键，然后定义从表的外键
  • 唯一约束——确保表中的一列数据没有相同的值，一个表可以定义多个唯一约束
  • 默认约束——在插入新数据时，如果该行没有指定数据，系统将默认值赋给该行
  • Check 约束——通过逻辑表达式来判断数据的有效性，用来限制输入一列或多列的值的范围

Compact 行格式

InnoDB 提供了 4 种行格式：

  • Redundant——古老，不紧凑
  • Compact——紧凑，5.0 之后引入，5.1 之后默认
  • Dynamic——基于 Compact 改进，5.7 之后默认
  • Compressed——基于 Compact 改进

几种连接查询

MySQL 的连接查询主要可以分为外连接、内连接、交叉连接。

  • 左外连接（LEFT JOIN）——显示左表中所有的数据及右表中符合条件的数据，右表中不符合条件的数据为 null

  • 右外连接（RIGHT JOIN）——显示右表中所有的数据及左表中符合条件的数据，左表中不符合条件的数据为 null

  • 内连接——只显示符合条件的数据
  • 交叉连接——使用笛卡尔积的一种连接，两两组合为新的关系

SQL 语句顺序和执行顺序

  • FROM——首先对关键字两边的表以笛卡尔积的形式执行连接，并产生虚表 V1。虚表就是视图，数据会来自多张表的执行结果
  • ON——对 FROM 连接的结果进行 ON 过滤，创建虚表 V2
  • JOIN——将 ON 过滤后的左表添加进来，创建新的虚表 V3
  • WHERE——对 V3 进行 WHERE 筛选，创建虚表 V4
  • GROUP BY——对 V4 中的记录进行分组操作，创建虚表 V5
  • HAVING——对 V5 进行过滤，创建虚表 V6
  • SELECT——将 V6 中的结果按照 SELECT 进行筛选，创建虚表 V7
  • DISTINCT——对 V7 中的结果进行去重，创建虚表 V8（如果使用了 GROUP BY 则无需 DISTINCT，因为分组时已经将列中唯一的值分成一组，每组只返回一行记录）
  • ORDER BY——对 V8 中的结果进行排序

什么是临时表

  • MySQL 在执行 SQL 语句的时候会临时创建一些存储中间结果集的表，这种表被称为临时表，临时表只对当前连接可见
  • 在连接关闭后，临时表会被删除并释放空间
  • FROM 中的子查询会用到临时表

数据库存储引擎

使用存储引擎可以创建、查询、更新、删除数据库。存储引擎可以理解为数据库的操作系统——不同的存储引擎提供的存储方式、索引机制等也不相同，就像 Windows 系统和 Mac 系统一样。在数据库开发时，为了提高 MySQL 的灵活性和高效性，可以根据实际情况来选择存储引擎。

顺带记一下：drop 删除表和数据库，delete 删除字段。

什么是子查询

子查询就是把一个查询的结果在另一个查询中使用。我的感觉就是下面说的内表查询。

SELECT * FROM user WHERE age = (SELECT max(age) FROM user);

where 和 in 的区别

  • WHERE——用于指定条件表达式来过滤数据，可以使用各种比较运算符和逻辑运算符
  • IN——用于判断某个字段的值是否属于给定的值列表中的任意一个

in 和 exists 的区别

一句话概括：in 先内后外，exists 先外后内；in 全部用索引，exists 仅在内表用索引。

  • 使用 exists 时会先进行外表查询，将查询到的每行数据带入到内表查询中看是否满足条件；使用 in 一般会先进行内表查询获取结果集，然后对外表查询匹配结果集，返回数据
  • in 在内表查询或外表查询过程中都会用到索引
  • exists 仅在内表查询时会用到索引
  • 一般来说，当子查询的结果集比较大、外表较小，使用 exists 效率更高；当子查询的结果集较小、外表较大时，使用 in 效率更高

例子：

INSERT INTO departments (id, department_name) VALUES
  (1, 'Sales'), (2, 'Marketing'), (3, 'HR');

INSERT INTO employees (id, name, department_id) VALUES
  (1, 'Alice', 1), (2, 'Bob', 1), (3, 'Charlie', 2), (4, 'David', 3), (5, 'Eve', 2);

IN 查询：

SELECT e.name, e.department_id
FROM employees e
WHERE e.department_id IN (
    SELECT d.id
    FROM departments d
    WHERE d.department_name IN ('Sales', 'Marketing')
);

先执行子查询，获取 departments 表中 department_name 为 Sales 或 Marketing 的 id；然后在 employees 表中查找 department_id 匹配这些 id 的记录。

EXISTS 查询：

SELECT e.name, e.department_id
FROM employees e
WHERE EXISTS (
    SELECT 1   -- 就是判断有没有这样的数据，有就返回 1，节约开销
    FROM departments d
    WHERE d.id = e.department_id
    AND d.department_name IN ('Sales', 'Marketing')
);

先从 employees 表中逐行读取数据；对于每一行记录，执行子查询。

int(10)、char(10)、varchar(10) 的区别

字符串就是规定的大小，int 表示的显示长度。

int(10) 中的 10 表示的是显示数据的长度，而 char(10) 和 varchar(10) 表示的是存储数据的大小。（联想一下 char(256) 是大小。）

几个数据类型的区别（red 面试考过数据结构）

DATE 和 TIMESTAMP：

  • DATE——用于存储日期值，不存时间，不会自动更新，需要手动更新（存储生日或事件日期）
  • TIMESTAMP——用于存储日期和时间值，可以设置为自动更新为当前时间（记录操作时间和需要时区转换）

char、varchar、text 的区别：

  • char——存储定长数据很方便，CHAR 字段上的索引效率极高。必须在括号里定义长度，可以有默认值。比如定义 char(10)，那么不论你存储的数据是否达到了 10 个字节，都要占去 10 个字节的空间（自动用空格填充），且在检索的时候后面的空格会隐藏掉，所以检索出来的数据需要记得用 trim 之类的函数去过滤空格
  • varchar——存储变长数据，但存储效率没有 CHAR 高。必须在括号里定义长度，可以有默认值。保存数据的时候不进行空格自动填充，而且如果数据存在空格时，当值保存和检索时尾部的空格仍会保留。另外 varchar 类型的实际长度是它的值的实际长度 +1，这一个字节用于保存实际使用了多大的长度
  • text——存储可变长度的非 Unicode 数据，最大长度为 2³¹-1 个字符。text 列不能有默认值，存储或检索过程中不存在大小写转换。后面如果指定长度不会报错，但这个长度不起作用——插入数据时超过你指定的长度还是可以正常插入

适用范围：

  1. char 长度固定，即每条数据占用等长字节空间，适合用在身份证号码、手机号码等
  2. varchar 可变长度，可以设置最大长度，适合用在长度可变的属性
  3. text 不设置长度，当不知道属性的最大长度时适合用 text

触发器

其实就是一个特殊的存储过程。当对一个表增、删、改的时候，对触发器里面的条件进行检查，如果成立就执行触发器里面的动作，否则不执行。可以确保安全性。

范式

  • 第一范式——字段具有原子性，不可拆分。每个单元格只能包含一个值，不能有重复组或多值属性

    错误例：(001, 张三, 数学,英语,物理)——「选课」是多值

  • 第二范式——依赖于全部主键，而非部分主键。仅针对复合主键，消除部分函数依赖

    错误例：成绩表（PK：学号 + 课程号）中，「学生姓名」只依赖学号、「课程学分」只依赖课程号

  • 第三范式——只依赖于主键，非主键字段互不依赖（消除传递函数依赖）

    错误例：学生表中「班主任」「班主任电话」依赖班级号，班级号依赖学号 → 传递依赖

  • BCNF——消除主属性对于码的部分和传递依赖
  • 第四范式——删除表中多对多的关系
  • 第五范式——消除连接依赖

SQL 执行的过程

SQL 执行会经历客户端、Server 层、存储引擎层 3 个部分。

Server 层包含连接器、查询缓存、分析器、优化器、执行器等核心组件：

  • 连接器——主要职责是管理连接、权限校验
  • 查询缓存——主要职责是为查询提供缓存
  • 分析器——主要职责是词法分析和语法分析，目的是识别 SQL 是做什么、有没有语法错误
  • 优化器——主要职责是关注 SQL 的性能，优化 SQL 语句怎么更好地执行，比如匹配索引、优化 join 查询的连接顺序
  • 执行器——主要职责是调用存储引擎的接口和返回结果
  • 存储引擎——主要职责是数据的存储和提取，给执行器提供接口

为什么我们需要数据库，用文件系统不行吗（tiktok 问）

根本原因在于：当数据和应用复杂到一定程度时，文件系统已经「撑不住」了。

维度 用文件系统 用数据库
持久化与完整性 数据存在文本文件里，程序崩溃或断电时容易损坏，且没有机制保证「转账时钱扣了但对方没收到」这类操作的原子性 提供 ACID 特性（原子性、一致性、隔离性、持久化）来避免上述问题
并发控制 10 个人同时编辑同一个 Excel 文件，要么互相覆盖，要么必须「排班」使用 行级锁、事务隔离级别等机制让成千上万用户同时读写同一张表而不会互相踩脚
索引与查询优化 在 100 万行的 CSV 文件里找，需要逐行扫描，可能几秒甚至几分钟 通过 B+ 树索引，同样查询只需毫秒级
运维层面 单机文件大小超过磁盘容量时需要手动分片、备份、迁移，复杂且危险 主从复制、分库分表，支持平滑迁移
结构化与一致性 JSON 文件存用户、另一个文件存订单，手动维护「用户删除后订单怎么办」，迟早出现孤儿数据 外键约束、触发器、存储过程确保关联数据始终同步，不会出现「订单指向不存在的用户」

小结

MySQL 的知识看着散，但其实是一棵树的三个分支：

  • 索引决定了查询有多快——B+ 树的高扇出 + 叶子链表，本质是在「磁盘 IO 次数」上做优化（三层搞定 2kw 数据）
  • 事务和锁决定了并发有多稳——MVCC 让读不加锁，Next-Key Lock 堵住幻读，隔离级别本质是在「一致性」和「并发度」之间选一个点
  • 分库分表 + 主从 + 优化决定了量大了怎么办——单库并发 2000 是天花板，往上就得拆；而拆分又带来一致性、延时、扩容迁移的新问题

一句话串起来：索引解决读，MVCC 解决写，分片解决量。
