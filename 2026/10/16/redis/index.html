这篇是我 Redis 面试准备的完整笔记，从「为什么快」讲到底层数据结构、持久化、部署方案和缓存一致性。原稿是一份问答清单，我按知识依赖关系重排成了现在的结构，并把散落的命令行输出还原成了可读的代码块。

标注说明：文中带「（美团二面）」「（重点问）」这类后缀的，是我自己记录的面试实际考频，保留了原样。

一、Redis 是什么

Redis 是一个 key-value 存储系统，作为一种 NoSQL 内存数据库（非关系型数据库），具有快速的数据访问和高效的数据存储能力，非常适合用作缓存的存储层。

它可以缓存计算结果、页面内容、数据库查询结果等，通过提高访问速度和响应速度来提升系统性能。缺点是对结构化查询的支持比较差。

在 Redis 中有一个核心对象叫 redisObject，用来表示所有的 key 和 value——用 redisObject 结构体来表示 String、Hash、List、Set、ZSet 五种数据类型。Redis 支持事务，且所有操作都是原子性的。

它最适合的两个场景是：缓存和消息队列。

为什么这么快（重点）

三个原因：

  • 基于内存——Redis 是基于内存存储实现的数据库
  • 合理的线程模型——多路 I/O 复用技术让单个线程可以高效处理多个连接请求，Redis 在 Linux 中使用 epoll 作为 I/O 多路复用技术的实现
  • 高效的数据结构——每种数据类型底层都做了针对性优化，目的就是追求更快的速度

既然这么快，为什么不用它做主数据库？

三个硬伤：

维度 问题
事务处理 Redis 只支持简单事务，不支持跨多个键的复杂事务处理
数据安全 没有提供像主数据库那样的安全机制，比如用户认证、访问控制
数据持久化 内存数据库，服务器崩溃或断电时数据可能丢失。虽然提供了持久化机制，但存在限制

二、线程模型

Redis 基于 Reactor 模式开发了网络事件处理器，称为文件事件处理器。

Reactor 模式是一种用于处理并发 I/O 操作的设计模式，核心思想是通过一个或多个线程来监听和分发 I/O 事件，将事件分发给相应的事件处理器进行处理。

文件事件处理器的组成结构为 4 部分：多个套接字、IO 多路复用程序、文件事件分派器、事件处理器。

因为文件事件分派器队列的消费是单线程的，所以 Redis 才叫单线程模型。

工作方式：

  • 文件事件处理器使用 I/O 多路复用程序来同时监听多个套接字，并根据套接字目前执行的任务为其关联不同的事件处理器
  • 当被监听的套接字准备好执行连接 accept、read、write、close 等操作时，与操作相对应的文件事件就会产生，这时文件事件处理器就会调用套接字之前关联好的事件处理器来处理这些事件

关于线程安全的两个层面（美团二面）

  • Redis 本身的设计没有线程安全问题，因为 Redis 是单线程模型
  • 但在某些情况下会出现复合操作的问题——比如两个线程都读取了 Redis 中存储的变量然后各自减一，这会导致两个线程同一时间读到的变量不一致，就出现了线程安全问题
  • 这种情况需要用 Redis 的原子操作 INCR，或者 Lua 脚本来确保一致性

三、数据结构

五种基本类型（重点）

类型 说明 底层实现
String 最常用的类型，值可以是字符串、数字或二进制 SDS
Hash 键值对集合 哈希表
Set 无序去重的集合，提供交集、并集等方法，实现共同好友、共同关注很方便 哈希表 + 整数集合
List 有序可重复的集合 双向链表 / 压缩列表
SortedSet 有序 Set，内部维护一个 score 参数来实现，适用于排行榜和带权重的消息队列 跳表 + 压缩列表

三种特殊类型

  • Bitmap——位图，可以认为是一个以位为单位的数组，每个单元只能存 0 或 1，数组下标在 Bitmap 中叫做偏移量。Bitmap 的长度与集合中元素个数无关，而是与基数的上限有关
  • HyperLogLog——用来做基数统计的算法。优点是在输入元素的数量或体积非常非常大时，计算基数所需的空间总是固定的、并且很小。典型场景是统计独立访客
  • Geospatial——主要用于存储地理位置信息并对其操作，适用场景如定位、附近的人

底层数据结构详解

压缩列表（ZipList）——一种用于紧凑存储列表和哈希表数据的数据结构。由一系列特定编码格式的连续内存块组成的顺序型数据结构（特殊的双向链表），每个内存块称为一个节点（entry）。每个节点可以存储一个字节数组或整数值，并根据实际数据动态调整节点长度。

  • 支持通过索引快速定位到指定位置的节点，可以在 O(1) 时间复杂度内实现随机访问
  • 适应于小规模数据

连锁更新问题：ziplist 在更新或新增时，如果空间不够需要对整个列表重新分配。当新插入的元素较大时，可能会导致后续元素的 prevlen 占用空间都发生变化，从而引起「连锁更新」，导致每个元素的空间都要重新分配，造成访问压缩列表性能下降。

listpack——类似压缩列表，但做了优化：没有记录前一个节点长度的字段，只记录当前节点的长度。当我们向 listpack 加入一个新元素时，不会影响其他节点的长度字段变化，从而避免了压缩列表的连锁更新问题，提高了内存使用效率。

SDS（简单动态字符串）——相比 C 语言字符串的三个优势：

  • 字符串长度处理——Redis 获取字符串长度的时间复杂度为 **O(1)**，因为长度就存在头部；而 C 语言中需要从头遍历，复杂度为 O(n)
  • 空间预分配——字符串修改越频繁，内存分配越频繁，就越消耗性能。SDS 在修改和空间扩充时，会额外分配未使用的空间，减少性能损耗
  • 惰性空间释放——SDS 缩短时不是立即回收多余内存，而是用 free 记录下多余空间，后续有变更直接复用，减少分配

跳跃表——在链表的基础上增加多级索引来提升查找效率。最底层的链表包含所有元素，上层链表包含间隔越来越大的元素，用于快速跳转。支持平均 **O(logN)**、最坏 O(N) 的节点查找，还可以通过顺序性操作批量处理节点。

跳表的查找过程：

  1. 从跳表的最高层开始，通常从头节点（header）出发，头节点的每个层级都指向该层级的第一个节点
  2. 在每一层上，沿着当前层的指针向右移动，直到遇到一个值大于目标值的节点，或者到达该层末尾。这个过程可以跳过大量不相关的节点
  3. 当在当前层无法继续向右移动时，就降低一层继续向右查找，重复直到到达最底层
  4. 在最底层逐个节点比较，直到找到匹配的目标节点，或确定目标节点不存在

跳跃表插入的过程也是从顶向下的，因为底层才是最完善的数据。复杂度同样是 logN。（字节一面拷打过）

quicklist——双向链表 + 压缩列表的混合体。quicklist 本身是一个链表，而链表中的每个元素又是一个压缩列表。

通过控制每个链表节点中压缩列表的大小或元素个数，来规避连锁更新问题——因为压缩列表元素越少或越小，连锁更新带来的影响就越小，从而提供更好的访问性能。它可以在列表两端快速插入删除，同时内部用压缩列表节省内存。

SortedSet 和 List 的异同

相同点：

  • 都是有序的
  • 都可以获得某个范围内的元素

不同点：

  • List 基于链表实现，获取两端元素快，访问中间元素慢
  • 有序集合基于散列表和跳跃表实现，访问中间元素时间复杂度是 O(logN)
  • 列表不能简单地调整某个元素的位置，有序集合可以（通过更改元素的分数）
  • 有序集合更耗内存

zset 为什么用跳跃表而不是平衡二叉树（美团二面）

  • 跳表更适合高效的有序范围查找——因为底层链表找到起点后就可以顺序遍历，非常适合 Redis 中的 zrange 操作。虽然查找、插入、删除上两者都是 logN
  • 实现复杂度低，便于维护——跳表本质是多层链表；相比之下 AVL 树在插入和删除时需要复杂的旋转和平衡调整
  • 跳表采用概率平衡而不是严格平衡，更加节约内存空间

四、Redis 事务

事务生命周期

  1. 使用 MULTI 开启一个事务
  2. 开启事务后，每次操作的命令会被插入到一个队列中，并不会真的执行
  3. EXEC 命令进行提交事务
127.0.0.1:6379> multi
OK
127.0.0.1:6379> set a 1
QUEUED
127.0.0.1:6379> set b 1 2
QUEUED
127.0.0.1:6379> set c 3
QUEUED
127.0.0.1:6379> exec
1) OK
2) (error) ERR syntax error
3) OK

一个事务范围内某个命令出错，不会影响其他命令的执行——所以不保证原子性。

WATCH 命令

WATCH 可以监控一个或多个键，一旦其中有一个键被修改，之后的事务就不会执行（类似于乐观锁）。执行 EXEC 命令之后，就会自动取消监控。

127.0.0.1:6379> watch name
OK
127.0.0.1:6379> set name 1
OK
127.0.0.1:6379> multi
OK
127.0.0.1:6379> set name 2
QUEUED
127.0.0.1:6379> set gender 1
QUEUED
127.0.0.1:6379> exec
(nil)
127.0.0.1:6379> get gender
(nil)

支持隔离性吗？保证原子性吗？支持回滚吗？

三个问题的答案：

  • 隔离性——Redis 是单进程程序，并且保证在执行事务时不会对事务进行中断，事务可以运行直到执行完所有队列中的命令为止
  • 原子性——Redis 单条命令是原子性执行的，但事务不保证原子性
  • 回滚——没有回滚。事务中任意命令执行失败，其余的命令仍会被执行

五、缓存三大经典问题（重点问）

缓存穿透

现象：查询一个一定不存在的数据。由于缓存不命中时需要从数据库查询，查不到数据则不写入缓存，这将导致这个不存在的数据每次请求都要到数据库去查询，进而给数据库带来压力。

解决：采用布隆过滤器，将所有可能存在的数据哈希到一个足够大的 bitmap 中，查询不存在的数据会被这个 bitmap 拦截掉，从而避免对 DB 的查询压力。

布隆过滤器的原理：当一个元素被加入集合时，通过 K 个哈希函数将这个元素映射成位数组中的 K 个点，把它们置为 1。查询时，将元素通过哈希函数映射之后会得到 k 个点——如果这些点有任何一个为 0，则被检元素一定不在，直接返回；如果都是 1，则查询元素很可能存在，才会去查询 Redis 和数据库。

缓存雪崩

现象：缓存中数据大批量到过期时间，而查询数据量巨大，请求都直接访问数据库，引起数据库压力过大甚至宕机。

解决：① 失效时间上加上一个随机数；② 加锁；③ 加上多级缓存。

当时答完这三条被 Redis 面试官追问了「只有一个吗？」，哈哈哈。

缓存击穿

现象：热点 key 在某个时间点过期的时候，恰好在这个时间点对这个 key 有大量并发请求过来，从而大量请求打到 DB。

解决：加互斥锁，比如加 Redis 的分布式锁 setnx，只让一个进程进行查询，然后把数据载入缓存中，后面就直接查缓存。

三者的区别（一句话记）

  • 穿透——查的是根本不存在的数据，缓存和 DB 都没有
  • 击穿——查的是某一个大热点 key，它刚过期
  • 雪崩——大批 key 同时过期，DB 被瞬间打垮

六、热 Key 问题

我们把访问频率高的 key 称为热点 key。

解决方案：

  • Redis 集群扩容——增加分片副本，将热 key 分散到不同的服务器中
  • 使用二级缓存——减少 Redis 的读请求（多加一个本地缓存，减少读 Redis 的次数）

七、持久化（重点）

持久化就是把内存的数据写到磁盘中，防止服务宕机导致内存数据丢失。

Redis 提供了 RDB 和 AOF（Append Only File）两种持久化机制。它的持久化文件加载流程如下：

RDB 一般是全量数据，AOF 一般是增量数据。

RDB

RDB 就是把内存数据以快照的形式保存到磁盘上。

具体来说，RDB 持久化是指在指定的时间间隔内，执行指定次数的写操作，将内存中的数据集快照写入磁盘。它是 Redis 默认的持久化方式。执行完后会在指定目录下生成一个 dump.rdb 文件（二进制文件），Redis 重启时通过加载 dump.rdb 文件来恢复数据。

  • 优点——可以做到大规模的数据恢复；使用单独子进程进行持久化，主进程不会进行任何 IO 操作，保证了 Redis 的高性能
  • 缺点——没有办法做到实时的持久化操作。一旦 Redis 异常退出，就会丢失最近一次持久化以后更改的数据

bgsave 是主流的触发 RDB 持久化的方式，执行过程：

  1. 执行 BGSAVE 命令
  2. Redis 父进程判断当前是否存在正在执行的子进程，如果存在，BGSAVE 命令直接返回
  3. 父进程执行 fork 操作创建子进程，fork 操作过程中父进程会阻塞
  4. fork 完成后，父进程继续接收并处理客户端请求，而子进程开始将内存中的数据写进硬盘的临时文件
  5. 当子进程写完所有数据后，用该临时文件替换旧的 RDB 文件

触发 RDB 的两种方式：

  • 手动触发——执行 SAVE 或 BGSAVE 命令。SAVE 命令执行快照的过程会阻塞所有客户端的请求，应避免在生产环境使用。BGSAVE 可以在后台异步进行快照，快照同时服务器还能继续响应请求，手动执行快照时推荐使用 BGSAVE
  • 被动触发——默认情况下执行 shutdown 命令时，如果没有开启 AOF 持久化功能则自动执行 BGSAVE；或者通过配置文件进行规定描述

AOF

AOF（append only file）持久化采用日志的形式记录每个写操作，通过写到一个缓冲区然后追加到文件，重启时再重新执行 AOF 文件中的命令来恢复数据。它主要解决数据持久化的实时性问题。

开启 AOF 后每执行一条写命令，Redis 就会将该命令写进 aof_buf 缓冲区，AOF 缓冲区根据对应的策略向硬盘做同步操作。默认情况下系统每 30 秒会执行一次同步操作。

AOF 操作流程：

  1. 所有的写入命令会追加到 AOF 缓冲区中
  2. AOF 缓冲区根据对应的策略向硬盘同步
  3. 随着 AOF 文件越来越大，需要定期对 AOF 文件进行重写，达到压缩文件体积的目的。AOF 文件重写是把 Redis 进程内的数据转化为写命令同步到新 AOF 文件的过程
  4. 当 Redis 服务器重启时，可以加载 AOF 文件进行数据恢复

优点：

  • AOF 可以更好地保护数据不丢失——可以配置 AOF 每秒执行一次 fsync 操作，如果 Redis 进程挂掉，最多丢失 1 秒的数据
  • AOF 以 append-only 的模式写入，所以没有磁盘寻址的开销（因为是往后追加），写入性能非常高

八、部署方案

单机版

单机部署，能承载的 QPS 大概在一万到几万不等。

主从模式

一主多从，主负责写。很轻松实现水平扩容，支撑读高并发。

缺点是 master 节点挂掉后需要手动指定新的 master，可用性不高，基本不用。

复制流程：

  1. 启动一个从节点时，它会发送一个 PSYNC 命令给主节点
  2. 如果是从节点初次连接主节点，会触发一次全量复制。此时主节点会启动一个后台线程，开始生成一份 RDB 快照文件
  3. 同时还会将从客户端新收到的所有写命令缓存在内存中。RDB 文件生成完毕后，主节点将 RDB 文件发送给从节点，从节点先将 RDB 文件写入本地磁盘，然后再从本地磁盘加载到内存中
  4. 接着主节点会将内存中缓存的写命令发送到从节点，从节点同步这些数据
  5. 如果主从之间网络出现故障、连接断开，会自动重连，连接之后主节点仅会将部分缺失的数据同步给从节点

哨兵模式

客户端连接 Redis 时先连接哨兵，哨兵会告诉客户端主节点的地址，然后客户端连接上进行后续操作。当主节点宕机时，哨兵监测到后会重新推选出某个表现良好的从节点成为新的主节点，然后通过发布订阅模式通知其他的从服务器，让它们切换主机。

故障判定与转移流程：

  1. 每个 Sentinel 以每秒钟一次的频率向它所知道的 Master、Slave 以及其他 Sentinel 实例发送一个 PING 命令
  2. 如果一个实例距离最后一次有效回复 PING 的时间超过指定值，这个实例会被 Sentinel 标记为主观下线
  3. 如果一个 Master 被标记为主观下线，则正在监视这个 Master 的所有 Sentinel 要以每秒一次的频率确认 Master 是否真正进入主观下线状态
  4. 当有足够数量的 Sentinel（大于等于配置文件指定值）在指定时间范围内确认 Master 确实进入了主观下线状态，则 Master 会被标记为客观下线
    • 若没有足够数量的 Sentinel 同意，Master 的客观下线状态就会被解除
    • 若 Master 重新向 Sentinel 的 PING 命令返回有效回复，Master 的主观下线状态就会被移除
  5. 哨兵节点会选举出哨兵 leader，负责故障转移的工作
  6. 哨兵 leader 会推选出某个表现良好的从节点成为新的主节点，然后通知其他从节点更新主节点信息

Redis Cluster

Redis Cluster 并没有使用一致性 hash，而是采用虚拟 slot（槽）分区的概念——一共分成 16384 个槽，每个节点负责维护一部分槽以及槽所映射的键值数据。将请求发送到任意节点，接收到请求的节点会将查询请求发送到正确的节点上执行。主要针对海量数据 + 高并发 + 高可用的场景。

最小配置 6 个节点以上（3 主 3 从），其中主节点提供读写操作，从节点作为备用节点不提供请求，只作为故障转移使用。

  • 通过哈希的方式将数据分片，每个节点均分存储一定哈希槽区间的数据，默认分配了 16384 个槽位
  • 每份数据分片会存储在多个互为主从的多节点上
  • 数据写入先写主节点，再同步到从节点（支持配置为阻塞同步）
  • 同一分片多个节点间的数据不保持一致性
  • 读取数据时，当客户端操作的 key 没有分配在该节点上时，Redis 会返回转向指令，指向正确的节点

两个端口：在 Redis Cluster 架构下，每个 Redis 要放开两个端口号，比如一个是 6379，另外一个就是加 1w 的端口号（如 16379）。

16379 端口用于节点间通信，也就是 cluster bus（用来进行故障检测、配置更新、故障转移授权）。cluster bus 使用 gossip 协议，用于节点间高效的数据交换，占用更少的网络带宽和处理时间。

九、内存管理

过期键的删除策略

Redis 同时使用了惰性过期和定期过期两种策略。

为什么不全部扫描？假设 Redis 当前存放 30 万个 key 且都设置了过期时间，如果每隔 100ms 就检查全部 key，CPU 负载会特别高，最后可能会挂掉。

所以：

  • 定期过期——每隔 100ms 随机抽取一定数量的 key 来检查和删除。最后可能会有很多已经过期的 key 没被删除
  • 惰性删除——在获取某个 key 的时候，Redis 会检查这个 key 如果设置了过期时间并且已经过期，此时就会删除

内存淘汰策略

Redis v4.0 前：

  • volatile-lru——当内存不足以容纳新写入数据时，从设置了过期时间的 key 中使用 LRU（最近最少使用）算法淘汰
  • allkeys-lru——当内存不足以容纳新写入数据时，从所有 key 中使用 LRU 算法淘汰

Redis v4.0 后：

  • volatile-lfu——LFU（Least Frequently Used，最少使用），从已设置过期时间的数据集中挑选最不经常使用的数据淘汰（实现为哈希表 + 频率桶 + 双向链表）
  • allkeys-lfu——当内存不足以容纳新写入数据时，从数据集中移除最不经常使用的 key

内存优化

可以好好利用 Hash、List、Sorted Set、Set 等集合类型数据，因为通常情况下很多小的 key-value 可以用更紧凑的方式存放到一起。

尽可能使用散列表（hashes）——当散列表里存储的数少时使用的内存非常小，所以应该尽可能将数据模型抽象到一个散列表里面。

十、缓存一致性

日常使用哪种缓存模式

Cache Aside Pattern（旁路缓存模式）——读的时候先查缓存，不命中再查 DB 并回填；写的时候先更新 DB，再删除缓存。

这里的删除，方法上也可以选择延时双删。

MySQL 与 Redis 如何保证双写一致性（重点）

三种方案：

  • 缓存延时双删——主要用于解决高并发场景下的问题。在第一次删除缓存后，设定一段短暂的延迟时间（如几百毫秒），然后在这段延迟结束后再次尝试删除缓存
  • 删除缓存重试机制——在执行数据库更新操作后尝试删除关联缓存项。如果首次删除失败（例如网络波动、缓存服务暂时不可用），系统进入重试逻辑，按照预先设定的策略（如指数退避、固定间隔重试）进行多次尝试
  • 读取 binlog 异步删除缓存——在数据库发生写操作时，将变更记录在 binlog 或类似事务日志中，然后使用专门的异步服务或监听器订阅 binlog 的变化。一旦检测到数据更新，便根据 binlog 中的操作信息定位，将这些需要更新缓存的数据发送到消息队列，消费者处理消息队列中的事件，异步地删除或更新缓存中的对应数据

十一、其他高频问题

分布式锁 SETNX

在分布式场景下，无法使用单机环境的锁来对多个节点上的进程进行同步，服务器上的进程需要协调访问共享资源。

Redis 的 SETNX（SET if Not eXists）命令可以在键不存在时设置值，从而实现锁的获取。成功返回 1 表示获取锁成功，返回 0 表示锁已被占用。

if self.redis.set(self.lock_key, self.identifier, ex=self.timeout, nx=True):
    print(f"线程 {self.identifier[:8]} 成功获取锁")
    return True

两个典型问题：

  • A 获取锁后崩溃 → 锁永不释放 → 死锁
  • A 执行超时、锁被 B 获取，A 执行完后 DEL → 误删 B 的锁

生产级方案：加过期时间（ex 字段）来防死锁：

SET lock:resource <唯一标识> EX 30 NX
# EX 30: 30秒过期时间（防死锁）
# NX: 仅当key不存在时才设置（互斥）
# <唯一标识>: 通常是 UUID + 线程ID，用于验证锁归属

然后附带 Lua 脚本——因为 Redis 单线程执行，可以保证「验证归属 + 删除」的原子性。

keys 命令的问题

  • Redis 的命令是单线程的，**keys 指令会导致线程阻塞一段时间**，直到执行完毕服务才恢复
  • scan 采用渐进式遍历来解决 keys 命令可能带来的阻塞问题，每次 scan 的时间复杂度都是 **O(1)**，适合数据量规模比较大的时候
  • scan 的缺点——在 scan 过程中如果有键的变化（增加、删除、修改），遍历过程可能会有问题：新增的键可能没遍历到、遍历出重复的键等。也就是说，scan 并不能保证完整遍历出所有的键

发布订阅机制

Redis 的发布订阅机制能帮我们在分布式系统中实现实时通信和数据共享：

  • 频道（Channel）——消息发布的主题，客户端可以订阅一个或多个频道
  • 订阅者（Subscriber）——监听特定频道的客户端，频道有消息发布时会收到消息。通过 SUBSCRIBE 命令订阅
  • 发布者（Publisher）——向特定频道发送消息的客户端。通过 PUBLISH 命令发送
  • 模式匹配（Pattern Matching）——Redis 支持模式订阅，允许订阅者订阅符合特定模式的频道

虚拟内存机制

Redis 的 VM（虚拟内存）机制就是暂时把不经常访问的数据（冷数据）从内存交换到磁盘中，从而腾出宝贵的内存空间用于其它需要访问的数据（热数据）。

通过 VM 功能可以实现冷热数据分离——热数据仍在内存中，冷数据保存到磁盘。这样就可以避免因为内存不足而造成访问速度下降。

pipeline 的作用

使用 pipeline 可以批量请求、批量返回结果，执行速度比逐条执行要快。

原生批命令（mset、mget）与 pipeline 的对比：

  • 原生批命令是原子性的，pipeline 是非原子性的——pipeline 中途异常退出，之前执行成功的命令不会回滚
  • 原生批命令只有一个命令，但 pipeline 支持多命令

大 key 怎么处理（重点）

  • value 是 string 时——可以使用序列化、压缩算法将 key 的大小控制在合理范围内，但序列化和反序列化都会带来额外的时间消耗。或者将 key 进行拆分，一个大 key 分为不同的部分，记录每个部分的 key，使用 multiget 等操作实现事务读取
  • value 是 list/set 等集合类型时——根据预估的数据规模来进行分片，不同的元素计算后分到不同的片

应用场景

  • 缓存热点数据，缓解数据库压力
  • 计数器——利用 Redis 原子性的自增操作，实现统计用户点赞数、访问数等

    Redis 的 INCR 命令是原子操作，意味着在多线程或多进程环境下可以保证计数的准确性，不会出现并发问题。每次执行 INCR 都会将键的值加 1 并返回新值

  • 分布式锁
  • 简单的消息队列——使用 Redis 自身的发布/订阅模式或者 List 来实现，实现异步操作
  • 限速器——限制某个用户访问某个接口的频率，比如秒杀场景用于防止用户快速点击带来不必要的压力

Memcached 和 Redis 的区别

维度 Redis Memcached
数据结构 支持多种数据类型 单一，仅用来缓存数据
持久化 支持 不支持，重启后数据消失
集群 提供主从同步机制和 cluster 集群部署，能提供高可用 没有原生集群模式，需依靠客户端实现往集群分片写入
速度 快很多 较慢
IO 模型 单线程的多路 IO 复用模型 多线程的非阻塞 IO 模型
value 大小上限 512MB 1MB

Redis 6.0 引入了多线程 IO，用来处理网络数据的读写和协议解析，但是命令的执行仍然是单线程。

十二、两个实际场景

1. 连续签到——对于特定的数据结构，设置一个过期的时间，一般用到 string 类型的数据结构。

2. 消息通知（list 作为消息队列）——使用场景是消息通知。例如当文章更新时，将更新后的文章推送到 ES，用户就能搜索到最新的文章数据。

小结

Redis 的知识点看着碎，但两条主线能串起来：

  • 快——内存 + epoll 多路复用 + 单线程无锁竞争 + 针对性优化的底层结构（SDS / 跳表 / listpack）
  • 稳——持久化（RDB 全量 + AOF 增量）保数据、主从/哨兵/Cluster 保可用、过期 + 淘汰策略保内存、Cache Aside + 双删保一致性

而缓存穿透 / 击穿 / 雪崩这三个问题，本质都是「DB 被绕过了」——区别只在于是查了不存在的数据、还是热点 key 过期、还是大批 key 同时过期。
